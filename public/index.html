What is the Shadow DOM?

“Shadow DOM enables you to attach a DOM tree to an element, and have the internals of this tree hidden from JavaScript and CSS running in the page.”
— MDN · developer.mozilla.org
“Shadow DOM is like your HTML going ‘this is my private room.’ It keeps its markup and CSS in its own little bubble so the rest of the page can’t mess with it, and it only lets outside content in through a <slot>—very ‘boundaries,’ very ‘do not disturb.’”
— Copilot GPT-5.2

Shadow DOM started as an internal browser technique for encapsulating native widget internals, then evolved through the Web Components effort into a standardized developer API for building encapsulated, reusable web UI components.

Browsers have used Shadow DOM internally for years to build native controls. You just couldn’t see — or style — what was inside.

  • Play / pause button
  • Scrubber & progress bar
  • Volume control
  • Fullscreen button
  • Captions menu

Every one of those controls lives in a hidden shadow tree the browser creates automatically. Shadow DOM makes the same capability available to your elements.

Shadow DOM ≠ Web Components

Web Components = 3 Specs

  • Custom Elements — define new HTML tags with their own behaviour via customElements.define()
  • Shadow DOM — attach a scoped, encapsulated DOM tree to any custom element
  • HTML Templates — declare inert, reusable markup with <template> and <slot>

Shadow DOM is the encapsulation layer. You can use each spec independently, but together they form a full component model.

Pouring the Foundation

The Document Object Model is a live, tree-structured representation of an HTML page that the browser builds after parsing markup.

  • Every tag becomes a node in the tree
  • Nodes can be elements, text, comments, or attributes
  • JavaScript reads and mutates it via document APIs

The DOM Tree

The browser parses this into a node tree — parent/child/sibling relationships that scripts and stylesheets traverse.

Document Fragments

              
                const fragment = document.createDocumentFragment();

                const li1 = document.createElement('li');
                li1.textContent = 'Item one';
                fragment.appendChild(li1);

                const li2 = document.createElement('li');
                li2.textContent = 'Item two';
                fragment.appendChild(li2);

                // Single reflow — fragment's children move into the DOM
                document.querySelector('ul').appendChild(fragment);

A DocumentFragment is a lightweight, in-memory DOM node that holds a subtree outside the live document.

Mutations inside the fragment cause zero reflows until it is attached — a stepping stone to the encapsulation the Shadow DOM takes further.

The <template> Element

            
              <template id="card-tmpl">
               <article>
                <h2 class="headline"></h2>
                <p class="summary"></p>
               </article>
              </template>
            
          
            
              const tmpl = document.getElementById('card-tmpl');

              // Deep-clone the inert tree and attach it
              const clone = tmpl.content.cloneNode(true);
              clone.querySelector('.headline').textContent = 'Canterbury';

              document.body.appendChild(clone);

A <template> holds inert HTML — parsed but never rendered — until you clone it into the document.

Shadow DOM builds on this — a shadow root is effectively a scoped, auto-managed template clone attached to an element.

How to use

Imperatively

            
              const section = document.querySelector('#demo-html');
              const shadow = section.attachShadow({ mode: 'open' });

              const newQuote = document.createElement('blockquote');
              newQuote.textContent = '"The more you share, the more your bowl will be plentiful."';

              const author = document.createElement('p');
              author.textContent = '- James S.A. Corey, ';

              const cite = document.createElement('cite');
              cite.textContent = 'The Expanse';
              author.appendChild(cite);

              shadow.appendChild(newQuote);
              shadow.appendChild(author);

With Custom elements

Open vs Closed

Think of Shadow DOM as a private room inside a house. In open mode, the room is still self-contained, but there’s a visible door, so code can step in and inspect it. In closed mode, the room still exists and still works, but the house doesn’t expose the door, so outside code can’t directly enter through the normal API.”

Letting the Light in

Styling

Letting the Light in

::part

The ::part pseudo-element is a “window” that allows CSS to target elements inside the Shadow DOM.

  • :root
  • :empty
  • :nth-child()
  • :nth-last-child()
  • :first-child
  • :last-child
  • :only-child
  • :nth-of-type()
  • :nth-last-of-type()
  • :first-of-type()
  • :last-of-type()

Use ::part()::hover and similar to work around these restrictions.

— MDN CSS Selectors

CSS Variables Always Pierce the Boundary

::part() lets you style from outside. But CSS custom properties are the intended theming hook — they inherit through shadow boundaries by design.

Regular CSS rules and class selectors are blocked. Custom properties (tokens) flow through. Use :host to consume them.

Opening Doors

<slot>

<slot>s are structural doors that permit Light DOM content to be “projected” into specific rooms your component defines.

::slotted()

The flip side of <slot> — style projected Light DOM content from inside the shadow root.

Only direct slotted children can be targeted — ::slotted() cannot reach deeper descendants.

Accessibility

Use real HTML semantics inside the shadow root Shadow DOM doesn’t replace semantic HTML. If something is a button, use a real button; if it’s a heading, use a real heading.

Be careful with slots
A slot is flexible, but that also means consumers can pass in content you weren’t expecting, which can break semantics or create confusing structure.

Relationships using IDs can get tricky across shadow boundaries.

  • label for=...
  • aria-labelledby
  • aria-describedby

Keep important labels close to the control they describe and prefer native labeling patterns where possible
